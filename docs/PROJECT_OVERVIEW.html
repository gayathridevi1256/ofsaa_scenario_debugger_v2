OFSAA Scenario Debugger

Project Overview  |  Version 1.0.0

What Is This Tool?

The OFSAA Scenario Debugger is an internal web application built to help the team investigate why an OFSAA alert scenario is not generating alerts.

When a scenario runs in OFSAA and produces no alerts, the usual process is manual — someone opens the log file, reads the SQL, runs queries in a database client, and tries to figure out which condition is filtering out all the data. This can take hours per scenario.

This tool automates that entire process. You upload the scenario log file, click Run, and within minutes the system tells you exactly which part of the SQL is the problem — and why.

The Problem It Solves

OFSAA scenarios are built using a chain of SQL queries called CTEs (Common Table Expressions). Each CTE feeds data into the next, like a production line. If any one CTE returns zero rows, no alert is generated.

Example chain:

Loan Data  →  Customer Filter  →  Risk Filter  →  Alert

If the "Risk Filter" step returns zero rows, the alert never fires. But why?

  • Is the underlying data simply not there?
  • Is a threshold (like minimum risk level) set too high?
  • Is a date filter cutting out all records?

Without this tool, answering that question means running each CTE manually in a database tool, one by one, until the empty one is found — then digging further to find the specific condition causing it. This tool does all of that automatically and presents the findings in a clear, visual interface.

How It Works — Step by Step

Step 1 — Upload the Log File
The user uploads the OFSAA scenario execution log file through the web interface. No database access is needed at this stage.
Step 2 — Read the Log
The system reads the log file and extracts the scenario name, business date, and the full SQL query that OFSAA executed.
Step 3 — Set the Batch Date
The system identifies the correct business date for the analysis — matching the date from the original log, not today's date.
Step 4 — Execute the Dataset Query
The main SQL query is run against the Oracle database to confirm the data environment and establish a baseline.
Step 5 — Parse the CTEs
The SQL is broken down into its individual building blocks. Each block is saved separately so it can be tested in isolation.
Step 6 — Execute Each CTE One by One
Each CTE is run against Oracle. If it returns rows, the next one is tested. When a CTE returns zero rows, that is the identified problem point.
Step 7 — Diagnose the Failing CTE
The system automatically investigates the failing CTE using two checks:
  • Data Unavailability: Are the source tables empty? Is a JOIN eliminating all rows due to no matching keys? Is the date range filter too narrow?
  • Threshold Analysis: Is a numeric condition (e.g. "risk score >= 9") set too high or too low? The system queries the actual data range and tells you exactly what the threshold should be.
Step 8 — Display Results with Actionable Suggestions
All findings are presented visually, including the exact SQL condition responsible and a plain-English recommendation — for example:

"Try reducing the Efctv_Risk_Lvl threshold to get results and try again."

What the User Sees

Login Screen

Simple username and password login. Access is controlled by an administrator.

Dashboard

  • Upload a log file or drag-and-drop it onto the page
  • Run multiple scenarios at once (batch mode)
  • View the full history of all previous runs
  • Results from a previous run are cached — re-opening the same scenario instantly shows past results without re-running the analysis

Results Screen

  • Live progress updates as each pipeline step runs
  • Each CTE shown as a card with a clear pass or fail status
  • Full diagnostic breakdown for the failing CTE
  • Threshold Suggestions panel showing the HRE parameter name, current setting, actual data range, and a plain-English fix suggestion
  • Option to re-run with fresh data at any time

Key Features

Feature Description
Automated Diagnosis No manual SQL execution required — the tool does it all
Real Database Queries Connects directly to the Oracle database (FCCMATOMIC) for accurate results
CTE-Level Breakdown Pinpoints exactly which step in the query chain fails
Threshold Suggestions Shows actual data range vs. current threshold setting with recommended values
HRE Parameter Names Maps database column conditions back to HRE configuration names (e.g. CUST_EFCTV_RISK_NB shown as Efctv_Risk_Lvl)
Batch Processing Run multiple scenario logs at the same time
Result Caching Previous results are saved; the analysis only re-runs when explicitly requested
Audit History Every run is logged with who ran it and when
User Management Admin can add and remove users

Typical Use Case

Scenario: OFSAA runs overnight. An alert scenario produces zero alerts.

Before this tool: An analyst spends 2–3 hours manually opening the log, running each CTE in a database tool, narrowing down the issue, and guessing at which threshold to change.

With this tool:
  1. Analyst downloads the scenario log from OFSAA
  2. Opens the Scenario Debugger in a browser
  3. Uploads the log file and clicks Run
  4. Within 1–2 minutes, the tool shows:
    "CTE 'RiskFilter' returned 0 rows.
        Condition: CUST_EFCTV_RISK_NB (Efctv_Risk_Lvl) >= 9
        Actual data range: 2 to 7
        Try reducing the Efctv_Risk_Lvl threshold to get results and try again."
  5. Analyst adjusts the threshold in HRE and re-runs the scenario
Time saving: 2–3 hours reduced to under 5 minutes.

Important Notes

  • This tool does not modify OFSAA, HRE, or any database settings. It only reads and diagnoses. All fixes must be applied manually in HRE.
  • A live connection to the Oracle database is required to run diagnostic queries. The tool cannot work offline.
  • Designed for scenarios using standard CTE-based SQL (the OFSAA default pattern).
  • Maximum log file size: 10 MB.
